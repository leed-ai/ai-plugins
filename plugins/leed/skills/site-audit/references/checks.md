# What the audit script checks

One row per `check` id that `scripts/audit.mjs` reports. Rule numbers are those of `../../site-patterns/SKILL.md`; read the rule and its detail file before explaining or fixing a finding.

`error` findings are rule breaks. In changed-files mode they are what fails the audit for site-publish. `review` findings need you to look before calling them anything.

## Templates (`src/**/*.hbs`)

The script skips `src/_includes/leed/` (the build replaces it), every `leed-*.hbs` template at any depth (the CLI copies them in for each build and removes them afterwards: sitemaps, feeds, redirects, the documentation layout), everything in an `_archive` folder at any depth (Eleventy ignores `**/_archive/**`, so nothing there is built, and the audit does not count it as using a partial or layout either), the `-DISABLED.hbs` scaffolds in `src/_includes/` (Leed's starters, which nothing calls), `src/static/`, and everything inside `{{!-- --}}`, `{{! }}` and `<!-- -->` comments. A layout those skipped templates name is not reported missing, and what Leed's own partials call is read from `--app-root` instead. A scaffold's own partial calls count only when something calls the scaffold. A `-DISABLED.hbs` page outside `src/_includes/` is a page Eleventy builds, so it is checked like any other. In a Markdown page, fenced code blocks and inline code are not read for partial calls, since an example there calls nothing; inside an HTML block they are read, because markdown-it passes an HTML block through raw and Leed's `process` shortcode renders the partial call in it. Markdown pages get no per-file checks; in changed-files mode each one is listed in `notes` as skipped, so a pass says nothing about it.

## Stylesheets (`tailwind/**/*.css`)

Comments, quoted strings and `url(…)` are masked first, so a hex in `[fill="#ECECFF"]`, `url(#grad)` or a comment is never a color.

| Check | Rule | Severity | Matches | Not matched |
|---|---|---|---|---|

A shadow or `filter` color, and a custom property in a Mermaid stylesheet, are `review` |
| `site-token` | 9 | error | A `--site-*` color set to anything but a `var()`, in any stylesheet (in changed-files mode, in every changed one); with `--app-root`, each `--site-*` color from Leed's `site-tokens.reference.css` that nothing sets (one finding on theme.css) | `--site-header-height`, which is a length |

## Whole repo (full mode only)

| Check | Rule | Severity | Matches |
|---|---|---|---|
| `missing-layout` | 8 | error | A layout named in `src/_data/pageTypeList.json`, in a template's frontmatter or in a data file Eleventy merges into a page (`*.11tydata.json`/`.js`, `dir/dir.json`, `about.json` beside `about.hbs`, `src/_data/layout.json`) that is not in `src/_layouts/` and is not one Leed provides. Frontmatter is read as gray-matter reads it: trailing comments, quoted keys, JSON with trailing commas, flow mappings and block scalars (`>-`, `|`). A value the script cannot read (an alias, a merge key, a tag, `eleventyComputed`, JavaScript frontmatter or a computed data-file value) is never reported |
| `unreferenced` | 13 | review | A partial, layout or stylesheet that no page (`.html` pages included), used partial, used layout, page type, data-file `layout`, `@import`/`@reference` (with or without the `.css` extension, which Tailwind adds), `svgDiagram "name"` argument (in a mustache or a subexpression such as `(svgDiagram "name")`), bracket-literal partial name (`{{> [svg/a] }}`), or partial name passed to a Leed partial that renders it (`{{#> leed/docs/shell header="my-header" }}`, or a `header` value in frontmatter or a data file) reaches, and that the build does not look up by name (rule 13's list, every eject destination, `empty.hbs`, the `-DISABLED.hbs` scaffolds, `@utility color-theme-*` files). Skipped, with a note, for partials when a template calls one by a computed name (including `svgDiagram` or such a hash value given by a variable, or a lookup partial given another context object); for layouts when there is no `pageTypeList.json` or a layout value cannot be read; and for both when `src/` holds a Nunjucks, Liquid or `.11ty.js` template, which the script does not read |
| `tier-override` | 13 | review | An override at an eject destination whose template the site's plan does not render (only with `--eject-json` whose listing names a tier; with no tier the listing omits gated templates, so the check is skipped with a note). Not unused: it takes effect if the plan changes |

## Marking a justified exception

- **A custom loop (rule 7):** put a `{{!-- … --}}` comment saying why no built-in collection can express the selection, ending within 5 lines above the `#each`.
- **An `!important` (rule 10):** name the Leed `!important` or inline style it answers in a comment just above the rule.
- **Anything else the rule genuinely allows** — a third party's logo in its own colors, for example — add a comment anywhere in the file reading `site-audit: allow <check>` (several checks separated by commas), followed by the reason. The list ends at the first word that is not a check id, so `allow literal-color, the logo is the vendor's` allows `literal-color` only. Every finding of that check in that file moves to `justified`, with the comment, so the reviewer still sees it. Each allowed check gets its own `justified` entry, and the text report prints the comment.

A justified entry is never a pass by default. Read the comment and say whether you accept the reason.
