# Site Assets Skill

You manage the Leed CMS asset manager from the command line. Two jobs, and they have different rules:

- **Getting files in.** `leed asset upload` puts local files into the CMS so pages can reference them. Read its JSON result and paste the `markdown` it returns into page content, or write the matching HTML into a Handlebars template.
- **Working with what is already there.** `leed asset list`, `get` and `set` find assets and change their metadata and labels; `leed asset export` downloads originals back out.

**The two halves differ in where they run.** `upload` is site-bound: it must run inside a site's checkout and takes its company and environment from that site. The other four are company-bound: they run anywhere and take `--company` and `-e, --env`, which come from the site when you happen to be inside a checkout. Outside one nothing is defaulted: `--company` is required, and `-e` too unless that company is logged in to exactly one environment; without them the command refuses with `invalid_arguments` and the exact flags to add.

## When to Use It

- A page needs an image, PDF/Office document, audio file or video that exists only on this machine (a screenshot, a downloaded logo, a folder of product photos, a whitepaper).
- A batch of files must be imported, for example the media from a site migration.
- You are about to write an image or document URL by hand. **Don't.** Asset URLs, image ids and `data-assetid` attributes come from the CMS; a hand-built URL breaks and is invisible to the asset manager. Upload the file and use the `markdown` the CLI returns, or the values it returns in template HTML.
- You are not sure whether a file is already in the CMS. The upload checks for you: identical bytes are never uploaded twice.
- You need to **find** an asset — by media type, by label, or by a word in its name or filename — to get its id, its URL or its current alt text (`leed asset list`, `leed asset get`).
- You need to **fix metadata in bulk**: alt text that is wrong, a caption to clear, labels to add or remove across a set (`leed asset set`).
- The user wants their **originals back**, because they are leaving the platform or have lost a source file (`leed asset export`).

Do **not** use it for template design files. Images that are part of a layout or partial's design (icons, backgrounds) live under `src/static/` like any other template asset, as the site-builder skill describes. `leed asset upload` is for content: things an editor could also add in the CMS asset manager, whether they end up in a CMS page body or in a `.hbs` page (a product photo, a downloadable PDF, a demo video).

## Why Use It

- **Deduplication.** Every file is hashed (SHA-256, plus a perceptual hash for raster images). An exact copy of an existing asset is reported, not uploaded, and you reuse that asset instead. Visually similar images are listed as `nearDuplicates` so you can choose.
- **CMS-generated alt text.** Raster images get alt text generated by the CMS on upload, and the returned `markdown` already carries it.
- **Resumable batches.** A folder upload writes a state file after every step. An interrupted run, a failed file or an interrupted video resumes where it stopped, without duplicating anything.
- **Traceable asset ids.** Each result carries the `assetId`, and the `markdown` references it (`data-assetid`, `assetId=`), so the asset manager knows which pages use which asset.

## Rules

- **`upload` runs from inside the site checkout** (`raw-content`, or any folder in it; `leed site list --json` shows where it is); `list`, `get`, `set` and `export` run anywhere and take `--company <companyId|domain>` and `-e, --env <name>` instead. What follows in this rule is about `upload`. Folder uploads write their state file in the working directory, which is inside that repository (see the next rule). The command refuses to run anywhere else (`not_a_site_repo`). It always uploads to the company and environment that site targets. You never pass or need a company id or environment, and you cannot target another site from here. The `<path>` you upload may be anywhere on disk.
- **Always pass `--json`.** The result is one JSON document on stdout, while progress goes to stderr. Read the envelope: `ok`, then `data`, or `error.code`, `error.message` and `error.hint`.
- **Authentication** is the user's `leed auth login` session for this site. On `not_authenticated` or `auth_expired`, stop and ask the user to run the command in `error.hint`. Don't try to log in yourself.
- **Keep the state file out of commits.** Folder uploads write `leed-assets.json` in the current directory, or wherever `--state` points, plus `<state>.lock` and a temporary `<state>.tmp-<pid>` copy while running. They record upload progress, including short-lived resumable upload URLs, and `leed site commit` stages everything git does not ignore. Run from the site folder, which is outside the `raw-content` repository, or keep `--state` outside the repo. If a state file must live inside `raw-content`, name it `leed-assets-<name>.json`, which the site's `.gitignore` ignores (`leed-assets*`). The command refuses a state path inside a git repository that does not ignore it, its `.lock` and its temp copy; the fix is in `error.hint`. Never commit `leed-assets*` files.
- **Labels must exist.** `--labels` takes comma-separated **label ids** (not names) from this company. Unknown ids are refused before anything is uploaded. The hint lists the valid ids when the company has 10 labels or fewer; with more, it points you to Settings > Labels in the CMS or the Leed MCP `list_labels` tool. Look ids up in `src/_data/labelList.json` or with the Leed MCP `list_labels` tool.

## How: One File

```bash
leed asset upload ./images/hero.png --json
leed asset upload ./docs/whitepaper.pdf --labels <labelId>,<labelId> --json
```

The type is detected from the file; pass `--type image|video|audio|document` (`docs` is an alias) to have the CLI check that the file is that type. The result has one entry in `data.entries[0]`:

- `status: "uploaded"`: use `assetId`, `url` and `markdown`.
- An exact duplicate fails with `error.code: "validation_failed"`, and `error.message`/`error.hint` name the existing asset's id. Reuse that asset (get its record with the Leed MCP asset tools, or its markdown from the asset manager) instead of uploading again.
- `nearDuplicates` (images only): similar images already in the CMS, with a distance (smaller is closer). The file was uploaded anyway. Mention them to the user if one looks like the same picture.

## How: A Folder (Two Steps)

A folder is prepared first, then saved:

```bash
# 1. Prepare: walk, hash and check duplicates. Uploads nothing; writes the state file.
leed asset upload ./media --type image --json
leed asset upload ./media --type document --recursive --extension .pdf,.docx --labels <labelId> --json

# 2. Save: upload everything still pending. Run it again to resume.
leed asset upload ./media --save --json
```

- `--type` is required to prepare, and a folder holds one type per batch. Files of other types are counted in `data.ignored` and left alone.
- `--recursive` includes subfolders. `--extension` (repeatable or comma-separated) scans only those extensions.
- `--state <path>` puts the state file somewhere else. Name it `leed-assets-<name>.json` (for example `--state leed-assets-photos.json`) or put it outside the repository, as the rules above describe. Pass the same `--state` to `--save`. The prepare result's `data.next` is the exact `--save` command to run.
- Read the prepare result before saving: `data.counts` and each entry's `status`. `rejected-duplicate` entries will not be uploaded. Their `duplicateOf.assetId` is the existing asset to reuse (`source: "cms"`), or `duplicateOf.relativePath` is the earlier file in this batch that will be uploaded instead (`source: "batch"`).
- `--labels` on `--save` replaces the labels stored at prepare. Stored labels are re-checked before uploading, so a label deleted since prepare is refused.

## Reading Results

Every entry (in the JSON result and in the state file) has `relativePath`, `type`, `status`, and once uploaded, `assetId`, `url`, `markdown` and `asset` (the full CMS record, including generated `altText`).

| status | meaning | what to do |
|---|---|---|
| `uploaded` | the asset exists | paste `markdown` into page content, or use it in a template (see Putting Assets in Pages) |
| `rejected-duplicate` | identical bytes already exist | reuse `duplicateOf.assetId` (after save, batch copies point at the uploaded asset too) |
| `pending` | prepared, not uploaded yet | run `--save` |
| `failed` | the upload did not complete (`error` says why) | run `--save` again; it retries |
| `stale` | the file changed or vanished after prepare | prepare again, then `--save` |
| `skipped` | this file cannot be uploaded (`error` says why) | tell the user |

`--save` exits non-zero (exit 3, the class of `upload_failed`) when any file failed, but the document is still `ok: true` with per-file results and the cause in `warnings`. Only a run-level problem (authentication, permissions, a bad state file) is `ok: false`. Test for non-zero, never for a particular number.

## Finding and Editing Existing Assets

These four take `--company` and `-e, --env` and run anywhere; outside a site checkout pass `--company` (and `-e` unless that company is logged in to one environment only), as no login is a default. Always pass `--json` when you need to read the result.

```bash
# Find: narrow by media type, label ids, or a search of name and filename
leed asset list --json
leed asset list --type image --q logo --json
leed asset list --label lbl_123,lbl_456 --limit 50 --json

# Inspect one asset, with its fields grouped by what applies to its media type
leed asset get as_12345 --json

# Change metadata; an omitted flag is left untouched
leed asset set as_12345 --alt-text "Acme logo on a white background"
leed asset set as_12345 --caption ""                  # a cleared caption, not an absent one
leed asset set as_12345 --add-labels lbl_123 --remove-labels lbl_456
leed asset set as_12345 --from-file ./patch.json --name "Hero image"
```

**Flags are refused by media type, and the refusal names both.** `--alt-text` and `--caption` are image-only; `--thumbnail-timestamp`, `--allow-fullscreen` and `--muted` are video-only; `--autoplay`, `--controls` and `--loop` are video and audio; `--description` is video, audio and document — images carry `caption` instead, so a `NULL` description on an image is structural rather than empty. `leed asset set --help` prints the whole matrix.

**Three label flags, and they are not interchangeable.** `--labels` **replaces** the asset's entire label set; `--add-labels` and `--remove-labels` leave the rest in place. Reach for the additive pair unless you genuinely mean to overwrite. All three take label **ids**, not names.

## Exporting Originals

`leed asset export` downloads asset originals into a folder. It is resumable, and the manifest it writes is its own record of progress.

```bash
leed asset export ./originals                  # every asset in the company
leed asset export ./logos --type image         # narrowed the same way as list
leed asset export as_12345 ./one-file          # a single asset; the destination is always last
leed asset export ./originals --concurrency 8  # 1-16, default 4
```

**`assets.json` in the destination folder is the resume record.** Run the same command again and finished files are skipped, expired links are re-issued, and a file already on disk whose SHA-256 matches is left alone. Delete `assets.json` to start over. It is plain JSON, so a user who would rather drive the downloads with `curl`, `xargs` or `aria2` can read the same file.

**It holds short-lived links to this company's private files**, so the command refuses a destination inside a git repository that would commit it. Never commit an `assets.json` from an export.

Two things to tell the user rather than treat as failures:

- **A video comes back as Cloudflare Stream's MP4 rendition, not the file that was uploaded.** Its bytes and its recorded SHA-256 differ from the original by design, so it is re-fetched on a resume rather than verified.
- **A video whose MP4 download is not ready yet is reported unavailable.** That is a wait, not an error: run the command again later.

## Putting Assets in Pages

An uploaded asset goes in one of two places:

- **CMS page content** (a page body you author through the CMS, for example with the Leed MCP page tools): paste the Leed Markdown in `markdown`.
- **A Handlebars template** the site-builder skill lets you edit (root `.hbs` pages, `src/_layouts/`, non-leed `src/_includes/`): write the HTML or helper call below. Markdown and `{% ... %}` shortcodes do not render in `.hbs` files.

Never write asset references into the CMS-managed content folders of the site repo (for example `src/blog/`).

### In CMS Page Content (Markdown)

Use the entry's `markdown` exactly as returned. Don't rebuild it from `url`:

- image: `![alt text =WxH](...){data-assetid="..."}`
- document: `[name](...){data-assetid="..."}`
- audio: `{% audio path="..." assetId="..." %}`
- video: `{% cloudflare videoId="..." assetId="..." %}`

### In Handlebars Templates (HTML)

Take every value from the upload result, never from a hand-built URL, and keep `data-assetid="<assetId>"` on the element: it is how the asset manager knows the template uses the asset. HTML-escape text you copy into attributes (`"` becomes `&quot;`, `&` becomes `&amp;`).

**Image.** Use the link target of `markdown` as the src: `/cdn-cgi/imagedelivery/<hash>/<imageId>/original`. Don't use `url` (the absolute `https://imagedelivery.net/...` form), which gets no responsive `srcset`. Take the alt text from `markdown` too (the text before ` =WxH`, which already falls back to the file name when there is no generated alt text), and `width`/`height` from `asset.originalWidth`/`asset.originalHeight`.

```hbs
<img src="/cdn-cgi/imagedelivery/<hash>/<imageId>/original" alt="<alt>" width="<originalWidth>" height="<originalHeight>" data-assetid="<assetId>" class="...">
```

A plain `<img>` with that src gets a responsive `srcset` added by the build. If `asset.svg` is `true`, add `data-responsiver="false"` (SVGs cannot use `srcset`). For one fixed size instead, use the `Image` helper, which swaps `original` for the variant you name and never adds a `srcset` (variants are listed in the site-builder skill's `references/handlebars-reference.md`):

```hbs
{{#Image "/cdn-cgi/imagedelivery/<hash>/<imageId>/original" "medium"}}alt="<alt>" width="<width>" height="<height>" data-assetid="<assetId>" class="..."{{/Image}}
```

Scale `width`/`height` to the variant's size, keeping the original aspect ratio.

**Document.** `url` is the site path `/f/<assetId>/<filename>`. Use the name from `asset.name` as the link text:

```hbs
<a href="/f/<assetId>/<filename>" data-assetid="<assetId>">Download the whitepaper</a>
```

**Audio.** `url` is the site path `/f/<assetId>/<filename>`. This is the markup `{% audio %}` renders:

```hbs
<audio data-assetid="<assetId>" controls>
  <source src="/f/<assetId>/<filename>" type="audio/mpeg">
  Your browser does not support the audio element.
</audio>
```

**Video.** `url` is the Cloudflare Stream player URL (`https://customer-<code>.cloudflarestream.com/<videoId>/iframe?...`). This is the markup `{% cloudflare %}` renders. The build loads the video tracker for an iframe with both `data-assetid` and `data-cloudflare-video`, and `embedded-cf-video video-player` gives it the player styles:

```hbs
<div class="embedded-cf-video video-player">
  <iframe data-assetid="<assetId>" data-cloudflare-video="true" src="<url>" allowfullscreen
    allow="accelerometer; gyroscope; encrypted-media; picture-in-picture;"
    title="Cloudflare video player"></iframe>
</div>
```

For a video that opens in a modal from a button, use the `leed/popup-video` partial with `videoAssetId="<assetId>"` and `videoSrc="<url>"`. The partial uses `videoSrc` as the iframe URL and appends `autoplay=true`, so pass the full `url`, not the video id. `FeatureVideo` only renders the page's own feature video, not an uploaded asset.

## Interrupted Uploads

- **Ctrl-C or a dropped connection** during `--save`: the state is saved as it goes. Run the same `--save` again.
- **Video**: a video upload creates a placeholder asset first. If it is interrupted, `--save` resumes into the same placeholder. For a single video file, rerun with `--resume-placeholder <assetId>` (the placeholder's id from the failed result) so a second placeholder is not created.
- **Another run in progress**: a second run against the same state file is refused (`validation_failed`, "Another leed asset upload is using ..."). Wait for the first run to finish. A lock left by a process that is gone is taken over automatically, so don't delete the `.lock` file yourself.

## If Cloudflare blocks a request

Cloudflare's firewall sits in front of the Leed CMS and now and then mistakes legitimate content for an attack. When it does, the request never reaches Leed.

1. **Recognize it.** The CLI fails with `request_blocked` (exit `5`). An MCP tool call, or any other request to the CMS, comes back with a 403 and an HTML page ("Just a moment…" or "Attention Required"), `server: cloudflare` or a `cf-ray` value, and no JSON error. It is not a permissions problem: do not ask for a different role or sign in again.
2. **Stop.** Retry the same write at most once. Never alter, encode, split or obfuscate the user's content to get past the filter: the content is theirs, and the false positive is Leed's to fix.
3. **Report it.** From the CLI, run the `leed feedback blocked` command in the error's `hint`; it carries the ray id, method, path and time (add `--excerpt-base64` from `error.request` when it is there). From MCP, call `report_blocked_request` with the `rayId`, the time as `occurredAt`, the method and path if you know them, the tool name and its argument names written as `name=` with no value as `command` (for example `update_page_body pageId= ops=`), and at most 2 KB of the body base64-encoded as `excerptBase64`. Never put the blocked text itself in `command` or `note`: the report crosses the same firewall.
4. **Tell the user.** Say what was blocked (which page, setting or asset, and which command or tool) and give the ray id, then continue with the rest of the work.

## Known Limitations

- Needs a `leed auth login` session; API keys and OIDC tokens cannot upload.
- If the response to creating an asset is lost **and** the CMS failed to record its content hash, a rerun cannot recognize that asset and may create a second copy.
- SVGs uploaded in the browser have no content hash, so they are not found as duplicates.
- An interrupted video leaves a placeholder asset until `--save` or `--resume-placeholder` reuses it.
- `export` needs a `leed auth login` session with permission to export assets, and issuing download links for originals takes a stronger permission than reading the library.
- One asset type per folder batch. Prepare each type separately, with its own `--state` (for example `leed-assets-images.json` and `leed-assets-docs.json`) if they share a folder.
